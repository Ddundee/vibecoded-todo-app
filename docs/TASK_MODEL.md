# Data model and priority logic

## Task

The core entity (`backend/app/models/task.py`). Every field the spec
asked for, plus two additions explained below:

| Field | Notes |
|---|---|
| `id`, `title`, `description` | |
| `status` | `inbox`, `todo`, `in_progress`, `blocked`, `completed`, `cancelled` |
| `priority` | `critical`, `high`, `medium`, `low` — manually set, never overwritten by scoring |
| `category` | free-text string, seeded with `LeetCode`, `school`, `project`, `personal`, `errands` |
| `tags` | list of strings (JSON column) |
| `created_at`, `updated_at`, `completed_at` | |
| `due_date`, `due_time` | the actual deadline |
| `estimated_duration` | minutes |
| `source` | `manual`, `quick_add`, `recurring`, `mcp`, `api`, or a future integration name |
| `external_reference`, `notes` | |
| `planned_for_date` *(addition)* | intentionally selected for a given day's plan, independent of `due_date` — this is what "plan a task for today without changing its deadline" means in the spec |
| `recurrence_rule_id`, `occurrence_date` *(addition)* | links a generated occurrence back to its `RecurrenceRule` template |

Computed, not stored (recomputed on every read so they can't go stale):
`is_overdue`, `priority_score`, `priority_reasons`.

## RecurrenceRule

A template (`title`, `category`, `priority`, `pattern`, ...) that
`services/recurrence.py` expands into concrete `Task` rows on demand —
whenever `get_today` (or the `tasks://today` MCP resource) runs, it calls
`ensure_occurrences_for_date` for the current day, which is idempotent: it
checks for an existing `Task` with the same `(recurrence_rule_id,
occurrence_date)` before creating one. Each occurrence is its own `Task`
row, so completing one occurrence never touches any other — history is
never corrupted by recurrence.

Patterns: `daily`, `weekdays`, `weekly` (every 7 days from `start_date`),
`specific_days` (explicit weekday list), `monthly` (day-of-month),
`custom_interval` (every N days from `start_date`).

## Priority score

`services/priority.py` computes a score for "what should I work on next"
— simple, additive, and always returned with human-readable reasons so an
AI (or you) can see exactly why a task ranked where it did. **It never
writes back to `task.priority`.**

| Signal | Points |
|---|---|
| Manual priority | critical +100 / high +70 / medium +40 / low +15 |
| Overdue | +30 to +50, scaling with days overdue |
| Due today | +30 |
| Due within 3 days | +15 |
| Due within 7 days | +5 |
| Planned for today | +20 |
| Quick win (≤15 min estimated) | +5 |
| Large effort (>120 min estimated) | −5 |
| Blocked status | −15 |

`get_priority_ranked_tasks` (MCP) and `GET /api/tasks/ranked` (REST) both
return tasks sorted by this score, each with its `priority_reasons` list.

## Today view

`services/tasks.get_today_bundle` assembles, for a given date:

1. Materializes today's recurring-task occurrences (see above)
2. **scheduled** — tasks with `planned_for_date == today`
3. **due_today** — tasks with `due_date == today`
4. **overdue** — open tasks with `due_date < today`
5. **recurring_today** — the subset of `due_today` generated by a recurrence rule
6. **suggested_high_priority** — up to 5 critical/high-priority tasks with
   no due date and not already planned/shown above (deduplicated against
   the other sections)
